Data: 02/11/2026 · Status: aceita

## Decisões

1. **Dados reais fora do Git.** `data/` (base real de 12.842 alunos e exportações do Supabase) e a cópia em `db/` tinham entrado no commit `ee7c027`. Na Fase 0 eles saíram do índice (`git rm --cached`) e `data/` foi para o `.gitignore`. Os arquivos continuam no disco de quem já tinha.
   - **Pendente (responsabilidade da equipe):** o histórico ainda contém os arquivos. Para limpar:
     ```bash
     # Com todos avisados e sem PRs abertos. Em um clone novo:
     pip install git-filter-repo
     git filter-repo --invert-paths \
       --path "src/Entrega 2/data" \
       --path "src/Entrega 2/db/base_unificada_asa-final.csv"
     git remote add origin <url>   # o filter-repo remove o remote
     git push --force --all && git push --force --tags
     # Cada membro apaga o clone antigo e clona de novo.
     ```
     Se o repositório já foi público, considere os dados expostos e avise a orientação do projeto (LGPD).
2. **Embeddings em 1024d (Cloudflare `@cf/baai/bge-m3`), sem fallback TF-IDF.** É o que roda em produção desde a Entrega 2, com o motivo explicado em `web/api/perguntar.py`. Se a vetorização falha, o agente se abstém e encaminha para o ASA. O `idf_table.json` da Entrega 1 fica como histórico.
3. **O front continua React 18 + Vite** (`web/`), em vez de HTML sem build. O app já está em produção no Vercel e a equipe domina a stack. A otimização é tarefa da sessão web (abaixo).
4. **`web/api/perguntar.py` continua onde está** até o backend FastAPI assumir o `/chat`, para o deploy atual não quebrar.
5. **`estudantes` desacoplado de `auth.users`** (migration 002). A fila de risco precisa de estudantes que nunca fizeram login. O vínculo com o login fica em `estudantes.perfil_id`.
6. **Recursão no RLS corrigida** (002). A policy de staff em `perfis` consultava `perfis` e entrava em loop. Agora as policies usam as funções `papel_atual()`, `eh_equipe_asa()` e `eh_admin()`, todas `security definer`.

## Avisos para as sessões

- **ml · regra 5:** `total_contatos` e `dias_desde_ultimo_contato` vêm da base de contatos, que mistura pedidos do estudante com contatos do ASA. Para que procurar o ASA nunca aumente o risco, o modelo deve contar só contatos ativos (`contatos_asa.origem = 'contato_ativo'`) ou retirar essas features.
- **ml · atributos sensíveis:** `Sexo`, `Estado Civil` e `Idade` estão na baseline. É preciso avaliar se ficam (com análise de viés por grupo em `ml/artifacts/`). Eles nunca aparecem como fator para o atendente.
- **web · otimização do React:**
  - rotas por papel com `React.lazy` + `Suspense`, para o estudante não baixar o bundle do atendente
  - `@supabase/supabase-js` só para auth, com todo o resto passando pela API
  - PWA: `manifest.webmanifest` + service worker com cache do shell e uma tela offline
  - fontes self-hosted (woff2, com subset latin) no lugar do Google Fonts
  - trocar `src/api/perguntar.js` por um cliente do contrato (`/chat`, `/casos`...), que trate `Erro.codigo` e propague `X-Request-ID`
  - migrar os componentes para os tokens novos e remover os aliases do fim de `tokens.css`
  - ligar o modo escuro por `prefers-color-scheme` depois da migração
  - tirar o proxy para a produção do `vite.config.js` quando o backend local existir
- **backend:** o contrato prevê `/risco/inferir` e `/risco/modelo`, além das rotas mínimas, para cumprir o item "endpoint de inferência" da definição de pronto.
